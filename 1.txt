2. PHASE 1 - FOUNDATION REFACTOR  (do this first, everything depends on it)
--------------------------------------------------------------------------------

2.1 [M][R] GENERIC REPOSITORY LAYER  -> closes G2
--------------------------------------------------
Problem: DataStore currently holds separate raw collections for Users,
Equipment, Sessions, MaintenanceLogs, Notifications. No generics evidenced.

Build:
  - interface Identifiable
        String getId();

  - class Repository<T extends Identifiable>
        private final Map<String, T> items = new HashMap<>();
        Optional<T> findById(String id)
        List<T> findAll()
        void save(T item)            throws DuplicateDataException
        void update(T item)
        void delete(String id)
        List<T> findBy(Predicate<T> criteria)     // generic filtering
        <R> List<R> mapTo(Function<T,R> mapper)   // bounded generic method

Then:
  - All entity classes implement Identifiable.
  - DataStore (Singleton, retained) now exposes:
        Repository<User>            users
        Repository<Equipment>       equipment
        Repository<Session>         sessions
        Repository<MaintenanceLog>  maintenanceLogs
        Repository<Notification>    notifications
        Repository<Payment>         payments       (added in Phase 4)

Why this ordering: the Repository's save() is where DuplicateDataException
is thrown, so exceptions (2.2) must be defined in the same phase.

Report/video talking point: bounded type parameters (<T extends Identifiable>)
+ a generic method with its own type parameter (<R>) = strong LO2 evidence.
One class satisfies the Generics requirement across all six entity types
and removes five near-duplicate collection blocks from DataStore.


2.2 [M] CUSTOM EXCEPTION HIERARCHY  -> closes G3
--------------------------------------------------
Build an abstract base so polymorphic catch blocks are demonstrable:

  abstract class IWFCException extends Exception
        - String errorCode
        - LocalDateTime timestamp
        - abstract String getUserFriendlyMessage();

  MANDATORY THREE (named in the brief):
  1. InvalidBookingException     extends IWFCException
        - thrown on: equipment/studio time clash
        - thrown on: booking outside operating hours (06:00-22:00)
        - thrown on: booking a session in the past
  2. UnauthorizedAccessException extends IWFCException
        - thrown on: Member attempting to open Admin logs / User Management
        - thrown on: Instructor attempting to assign maintenance tasks
        - MUST be thrown at the Facade layer, not merely hidden in the UI
  3. DuplicateDataException      extends IWFCException
        - thrown on: registering equipment with an existing ID
        - thrown on: registering a user with an existing email

  ADDED VIA PAYMENTS (Phase 4) - extends the hierarchy beyond the minimum:
  4. PaymentFailedException      extends IWFCException
  5. InsufficientFundsException  extends PaymentFailedException

CRITICAL POINT: the current build validates permissions at the Facade but
does not THROW. Change the Facade to throw UnauthorizedAccessException and
let the UI catch it and raise a red Toast notification. The brief requires
exception handling, not access gating.

2.3 [E] UNAUTHORISED ACCESS AUDIT LOG
--------------------------------------------------
Every UnauthorizedAccessException caught at the Facade writes an
AuditEntry (who, what, when, denied reason) into a Repository<AuditEntry>.
Admin-only view. Cheap to build, turns an exception requirement into a
visible demoable feature.

3. PHASE 2 - BEHAVIOURAL PATTERNS  -> closes G1
--------------------------------------------------------------------------------

3.1 [M] OBSERVER PATTERN - Notification Engine  [R]
--------------------------------------------------
The existing Notification Centre is Observer in spirit. Formalise it:

  - interface EventObserver
        void onEvent(SystemEvent event);
  - abstract class EventPublisher
        private final List<EventObserver> observers
        void subscribe / unsubscribe / notifyObservers(SystemEvent)
  - Concrete observers:
        NotificationObserver   -> creates in-app notification + toast
        AuditObserver          -> writes to audit log
        MaintenanceAlertObserver -> escalates High urgency items

  Publishers: MaintenanceService (status change), BookingService (booking
  confirmed/cancelled), PaymentService (payment completed/failed),
  EquipmentService (usage threshold breached).

  The brief explicitly requires notifications to fire AUTOMATICALLY when a
  maintenance request status changes - Observer is the correct mechanism
  and directly satisfies that functional requirement.

3.2 [E] STRATEGY PATTERN - Payments
--------------------------------------------------
Covered in full in Phase 4. Second Behavioural pattern; the runtime swap of
payment method is the cleanest polymorphism demo in the whole system.

3.3 [E] COMMAND PATTERN - Admin actions with undo  (OPTIONAL / STRETCH)
--------------------------------------------------
  interface Command { void execute(); void undo(); String describe(); }
  Implementations: AddEquipmentCommand, DeactivateEquipmentCommand,
                   AssignMaintenanceCommand, EditEquipmentCommand
  CommandInvoker holds a Deque<Command> history; Admin gets an "Undo last
  action" button.
  Strong video moment. Build ONLY if Phases 1-5 are complete and stable.

4. PHASE 3 - FIX THE FUNCTIONAL REQUIREMENTS  -> closes G5 + smaller gaps
--------------------------------------------------------------------------------

4.1 [M] TIME-CLASH DOUBLE-BOOKING PREVENTION  -> closes G5
--------------------------------------------------
Current build prevents OVERBOOKING (class capacity). The brief requires
preventing DOUBLE-BOOKING of the same equipment or studio at the same time.
These are two different validations. Both must exist.

  BookingService / SchedulingValidator:
    boolean overlaps(TimeSlot a, TimeSlot b)
        -> a.start < b.end && b.start < a.end
    validateNoEquipmentClash(equipmentId, slot)  -> InvalidBookingException
    validateNoRoomClash(roomId, slot)            -> InvalidBookingException
    validateOperatingHours(slot)                 -> InvalidBookingException
    validateCapacity(session)                    -> InvalidBookingException

  This validator is the PRIMARY target of the JUnit suite in Phase 5.
  Keep it as a separate, dependency-free class so it is trivially testable.

4.2 [M] CUMULATIVE USAGE HOURS -> AUTO MAINTENANCE TRIGGER
--------------------------------------------------
Brief requires usage logs tracking cumulative hours to trigger preventative
maintenance alerts. Currently only a visual usage ring exists - no logic.

  - Equipment gains: double cumulativeUsageHours, double maintenanceThreshold
  - UsageLog entity: equipmentId, sessionId, hoursAdded, recordedAt
  - On session completion -> EquipmentService.recordUsage(...)
  - If cumulativeUsageHours >= threshold:
        auto-create MaintenanceLog (urgency = Medium, status = Pending)
        publish event -> Observer fires notification to Admin
  - Reset counter to 0 when maintenance marked Completed.

  This chains three required features (usage logs -> maintenance -> auto
  notification) into one 30-second demo sequence. High value for the video.

4.3 [M] FULL EQUIPMENT LIFECYCLE
--------------------------------------------------
Brief requires ADD, EDIT and DEACTIVATE. Build currently has add + view only.
  - editEquipment(...)  -> Admin only, throws UnauthorizedAccessException
  - deactivateEquipment(id) -> soft delete (active flag), never hard delete;
    deactivated units must not appear as bookable.

4.4 [M] ALIGN ENUM NAMING WITH THE BRIEF
--------------------------------------------------
  EquipmentStatus: Active/Maintenance/Out of Order
        -> RENAME to OPERATIONAL, FAULTY, UNDER_MAINTENANCE (+ DEACTIVATED)
  Urgency: Low/Medium/High/Critical
        -> Brief specifies Low/Medium/High only.
        -> KEEP Critical (the pulsing red UI is a strength) BUT add one
           sentence in the report justifying it as a deliberate extension.
  MaintenanceStatus: Pending/In Progress/Resolved
        -> RENAME to PENDING, ASSIGNED, COMPLETED  (brief's exact wording)

  Free marks. The marker will pattern-match against the brief's vocabulary.

4.5 [E] RECURRING WEEKLY SESSIONS
--------------------------------------------------
The ONLY enhancement the brief calls "highly encouraged". Do not skip.
  - RecurrenceRule: dayOfWeek, startTime, duration, weeksToRepeat
  - SessionFactory (Creational pattern #2) generates the session instances
  - Each generated instance runs through the full clash validator
  - Partial failure handling: if week 3 clashes, report it and create the
    rest rather than aborting the whole series.

5. PHASE 4 - PAYMENT GATEWAY & PAYMENT METHODS  -> G6
--------------------------------------------------------------------------------
DESIGN INTENT: payments are NOT mentioned in the brief and earn nothing on
their own. They are justified here because they are the cleanest possible
carrier for the Strategy pattern, they extend the exception hierarchy, and
they give the JUnit suite non-trivial branching logic to test. Frame it in
the report as "extending the domain model to demonstrate runtime
polymorphism", not as "I added a payments feature".

5.1 STRATEGY PATTERN - PAYMENT METHODS
--------------------------------------------------
  interface PaymentStrategy
        PaymentResult pay(double amount, PaymentContext ctx)
                throws PaymentFailedException;
        String getMethodName();
        double calculateProcessingFee(double amount);

  Implementations (each with a DIFFERENT fee rule = real polymorphism):
        CardPayment            - 2.5% fee, validates card number/expiry
        CashPayment            - 0% fee, requires at-counter confirmation
        BankTransferPayment    - flat LKR 50, requires reference number
        DigitalWalletPayment   - 1.5% fee, validates wallet ID

  PaymentContext carries method-specific data without polluting the
  interface (card no, wallet id, reference, etc.).

  Runtime selection: member picks method in the UI -> PaymentService
  swaps the strategy object -> identical call site, different behaviour.
  THIS IS THE POLYMORPHISM DEMO FOR THE VIDEO.

5.2 SIMULATED GATEWAY  (DO NOT integrate a real SDK)
--------------------------------------------------
  class MockPaymentGateway
        - authorise(): simulated latency (200-800ms), deterministic
          success/failure based on a seeded flag so DEMOS ARE REPEATABLE
        - forceFailureMode(boolean) for the intentional failing JUnit test
        - returns transaction reference

  Rationale: brief states database integration is not required and data may
  be hard-coded. A real gateway adds network dependency during the video
  demo and earns zero extra marks. Say this explicitly in the report -
  justifying a deliberate scope decision reads as maturity, not as a
  shortcut.

5.3 PAYMENT ENTITY & MEMBER PROFILE HISTORY
--------------------------------------------------
  class Payment implements Identifiable
        paymentId (PAY-0001...)   memberId
        amount                     processingFee
        totalCharged
        PaymentMethod (enum)       PaymentStatus enum:
                                     PENDING / COMPLETED / FAILED / REFUNDED
        LocalDateTime paidAt       transactionReference
        String description         (e.g. "Monthly Membership - October")
        PaymentPurpose enum: MEMBERSHIP_FEE / SESSION_BOOKING /
                             PERSONAL_TRAINING / DAY_PASS / MERCHANDISE

  UI - third column of the existing User Management panel:
        - Transaction table: date, description, method, amount, status badge
        - Status colour coding reusing the existing badge CSS
        - Filter by purpose and by date range
        - CRITICAL: the existing "Total Payments" analytics figure must be
          DERIVED from this list (a reduce over Repository<Payment>), not a
          hard-coded number. That is the whole point of adding the entity.

  Also surface: last payment date, next due date, outstanding balance,
  and a payment-method breakdown feeding the existing chart components.

5.4 PAYMENT EXCEPTIONS
--------------------------------------------------
  PaymentFailedException      - gateway declined, invalid card, timeout
  InsufficientFundsException  - extends PaymentFailedException
  Demonstrates a multi-level hierarchy + polymorphic catch:
        catch (PaymentFailedException e)  // catches both

5.5 OUT OF SCOPE - DO NOT BUILD
--------------------------------------------------
  Real Stripe/PayPal SDKs, refund workflows, tax/invoice numbering,
  multi-currency, saved card tokenisation, recurring auto-billing.
  All plausible-sounding, none assessed, all add failure surface.

6. PHASE 5 - JUNIT TEST SUITE  -> closes G4  (HIGHEST MARK IMPACT)
--------------------------------------------------------------------------------
This is the single biggest gap. The rubric's upper bands all depend on a
thorough test plan, findings, and reflection on bugs found and fixed.

Framework: JUnit 5 (Jupiter) via Maven. Add surefire plugin.

6.1 [M] SESSION SCHEDULING & VALIDATION TESTS
        - books into an empty slot                       -> succeeds
        - exact same equipment, same time                -> InvalidBooking
        - partial overlap (10:00-11:00 vs 10:30-11:30)   -> InvalidBooking
        - back-to-back (10:00-11:00 vs 11:00-12:00)      -> succeeds
                                                    (BOUNDARY CASE - test it)
        - same room, different equipment, same time      -> InvalidBooking
        - booking at 05:59 / 22:01                       -> InvalidBooking
        - booking a full-capacity session                -> InvalidBooking
        - @ParameterizedTest over a set of overlap cases

6.2 [M] MAINTENANCE WORKFLOW TRANSITION TESTS
        - PENDING -> ASSIGNED                            -> valid
        - ASSIGNED -> COMPLETED                          -> valid
        - PENDING -> COMPLETED (skipping assignment)     -> rejected
        - COMPLETED -> PENDING (reopening)               -> rejected
        - status change fires exactly one notification   -> Observer verified
        - completing maintenance resets usage counter to 0

6.3 [M] INTENTIONAL FAILING TEST - EXCEPTION VERIFICATION
        Brief requires AT LEAST ONE deliberate failing test proving custom
        exceptions are correctly thrown AND handled.

        Implement as an assertThrows block that proves the error path:
          - Member calls facade.viewMaintenanceLog()
                -> assertThrows(UnauthorizedAccessException.class, ...)
          - registerEquipment with an existing ID
                -> assertThrows(DuplicateDataException.class, ...)
          - MockPaymentGateway.forceFailureMode(true), then pay()
                -> assertThrows(PaymentFailedException.class, ...)

        Also assert on the exception CONTENTS (errorCode, user-friendly
        message), not just the type. That is what separates a 60s answer
        from a 70s+ answer.

        DOCUMENT IT CLEARLY: label these in the report as deliberate
        negative-path tests so the marker does not read a red test as a
        defect.

6.4 [M] GENERIC REPOSITORY TESTS
        - save/findById/delete round trip across TWO different entity types
          using the SAME Repository<T> class - this is the proof that the
          generic abstraction actually works.

6.5 [E] PAYMENT STRATEGY TESTS
        - each strategy returns its correct processing fee
        - strategy swap at runtime changes behaviour with an identical call
        - insufficient funds -> InsufficientFundsException

TARGET: 25-30 tests minimum. Screenshot the green run AND the documented
negative-path results for the report.

11. PHASE 7 - FITNESS PLANS & INSTRUCTOR SELECTION  [E]  (added v1.1)

DESIGN INTENT: like payments, fitness plans are not named in the brief. They
are justified here because (a) enrolment collides with the SAME clash
validator built in 4.1, giving the JUnit suite far richer branching, (b) the
plan catalogue is a natural Factory/Builder use case = Creational pattern #2,
(c) instructor reassignment is a genuine state-transition workflow that
mirrors the maintenance workflow already being tested, and (d) it finally
gives the Member role real agency - currently Members can only view and book.

Frame it in the report as "extending the domain model so the Member actor has
meaningful behaviour", NOT as "I added more features".

11.1 FITNESS PLAN DOMAIN MODEL
--------------------------------------------------

        planId, name, description
        PlanCategory category (enum)
        DifficultyLevel level: BEGINNER / INTERMEDIATE / ADVANCED
        int durationWeeks
        int sessionsPerWeek
        double monthlyFee
        List<String> requiredEquipmentTypes

        abstract double calculateMonthlyFee();      // POLYMORPHIC
        abstract String getProgressionSummary();    // POLYMORPHIC

  Three concrete subclasses - this is the INHERITANCE + POLYMORPHISM evidence

11.5 INSTRUCTOR CHANGE / REASSIGNMENT  <- the feature you actually asked for
--------------------------------------------------
  class InstructorChange
        changeId, enrollmentId
        previousInstructorId, newInstructorId
        ChangeReason enum: SCHEDULE_CONFLICT, INSTRUCTOR_UNAVAILABLE,
                           PERSONAL_PREFERENCE, SPECIALISATION_MISMATCH,
                           INSTRUCTOR_LEFT, PERFORMANCE_CONCERN
        String notes, requestedAt, ChangeStatus: PENDING/APPROVED/REJECTED
        approvedByAdminId

  requestInstructorChange(enrollmentId, newInstructorId, reason) validates:
        - requester owns the enrolment  -> else UnauthorizedAccessException
        - new instructor != current                (reject no-op)
        - new instructor holds required specialisation
        - new instructor under maxTrainees         -> InstructorUnavailable
        - new instructor's availability has no clash  -> REUSES 4.1 VALIDATOR
        - cooling-off: max 2 changes per enrolment per 30 days
          (prevents abuse; a nice realistic business rule to defend in viva)

  POLICY DECISION - make this explicit in the report:
        Members REQUEST a change; an Admin APPROVES it. Auto-approve only
        when reason = INSTRUCTOR_UNAVAILABLE or INSTRUCTOR_LEFT (system's
        fault, not the member's). This preserves the Member/Admin authority

12.2 THE UI/UX TECHNIQUES TO IMPLEMENT
--------------------------------------------------
These are the specific details that make the reference look premium. Each is
cheap in JavaFX/CSS:

     8px inset. Label goes 500-weight. Animate fill-in over 150ms rather
     than snapping.

  b) DRAG HANDLES ON REORDERABLE ITEMS
     The 6-dot grid icon in the reference (Dashboard, Reports) signals
     drag-to-reorder. Implement real reordering with JavaFX drag-and-drop
     and persist order per user in DataStore. This is the ONE piece of the
     sidebar with genuine engineering substance - mention it in the video.

  c) EXPAND/COLLAPSE WITH GUIDE LINE
     Children indented ~20px with a 1px vertical dotted guide line at the
     indent origin (reference shows this clearly). Animate height with a
     Timeline + easing; rotate the parent's chevron 90deg in the same
     150-200ms window.

  d) ICONOGRAPHY
     Thin monoline, 16px, consistent 1.5px stroke, matching the label's
     optical weight. Use Ikonli (FontAwesome5 / Material pack) via Maven -
     do NOT hand-draw SVG paths. Icons inherit text colour so theming is
     free.

  e) TYPOGRAPHY & RHYTHM
     Labels 13-14px, 400 weight, ~0.1px letter-spacing. Row height 36-40px.
     Icon-to-label gap 12px. Group padding 8px vertical. Consistent 4px
     spacing grid throughout - inconsistent gaps are what make homemade UIs
     look homemade.

  f) HAIRLINE DIVIDERS
     1px at ~8% opacity of the foreground colour, inset 12px from both
     edges. Never a full-bleed solid line.

  g) HOVER STATE

     HAND. No scaling on nav rows (scaling suits cards, not lists).

  h) COLLAPSIBLE RAIL
     Toggle between 240px expanded and 64px icon-only. Animate width over
     200ms with Interpolator.EASE_BOTH; fade labels out over the first

  i) NOTIFICATION BADGES

     When the rail is collapsed, degrade to a 6px dot on the icon corner.

  j) FOCUS / ACCESSIBILITY
     Visible focus ring on keyboard Tab, full arrow-key traversal, and
     Enter/Space activation. Cheap to add, and it is defensible EDGE
     (Ethical/Digital) evidence in the report.

  k) SCROLL BEHAVIOUR
     Group headers stay put; only the item list scrolls. Hide scrollbar

13.1 COMMAND PATTERN WITH UNDO  (PROMOTED FROM STRETCH - BUILD THIS)
--------------------------------------------------
Best remaining idea. Second Behavioural pattern, textbook abstraction +
polymorphism evidence, and the single strongest demo moment in the video.

  interface Command
        void execute() throws IWFCException;
        void undo()    throws IWFCException;
        String describe();          // for history UI + audit log
        boolean isUndoable();

  Implementations (Admin actions only):
        AddEquipmentCommand          undo -> remove
        EditEquipmentCommand         undo -> restore previous snapshot
        DeactivateEquipmentCommand   undo -> reactivate
        AssignMaintenanceCommand     undo -> revert to PENDING, clear tech
        ApproveInstructorChangeCommand  undo -> restore prior instructor
        CancelSessionCommand         undo -> reinstate session + bookings

  class CommandInvoker
        private final Deque<Command> undoStack = new ArrayDeque<>();
        private final Deque<Command> redoStack = new ArrayDeque<>();
        void run(Command c)   // execute, push, clear redo
        void undoLast()       // pop, undo, push to redo
        void redoLast()
        List<String> getHistory()   // uses describe()

  CRITICAL DESIGN POINTS (these are what separate a good mark from a average
  one - be ready to discuss them):
    - EditEquipmentCommand must snapshot the FULL previous state on
      execute(), not just the changed field. Implement a copy constructor
      or a memento-style snapshot on Equipment.
    - Commands that already fired notifications must NOT re-fire on undo.
      Pass a "silent" flag into the Observer publish call during undo, or
      publish an explicit ACTION_REVERTED event instead. Getting this wrong
      is a realistic bug - and a GREAT one to document in the video's
      "bugs identified and fixed" reflection.
    - isUndoable() returns false for anything with external side effects
      (a COMPLETED payment must never be silently undone - issue a refund
      record instead).

  UI: Admin header gets Undo / Redo buttons + a slide-out "Action History"
  panel listing describe() output with timestamps. Wire Ctrl+Z / Ctrl+Y.

  Integrates with 2.3 Audit Log - every Command execution and undo writes
  an AuditEntry, so the audit trail and the undo stack share one source.

  DEMO SCRIPT for the video: deactivate a treadmill -> it greys out and
  disappears from bookable equipment -> Ctrl+Z -> it returns, fully
  restored. 20 seconds, instantly legible to the marker.

  JUnit:
        - execute then undo restores exact prior state (assert field-by-field)
        - undo on empty stack -> handled gracefully, no exception leak
        - redo after undo reapplies correctly
        - COMPLETED payment command -> isUndoable() == false
        - undo does NOT duplicate notifications (Observer call count == 0)


13.2 EQUIPMENT AS A COMPOSITE  -> second Structural pattern
--------------------------------------------------
Your data already has zones (Cardio Zone, Studio A), so the hierarchy exists
implicitly. Make it explicit and recursive.

  interface EquipmentComponent
        String getName();
        double getTotalUsageHours();
        int getMaintenanceCount();
        int getOperationalCount();
        void display(int depth);        // indented tree print - console demo

  class SingleEquipment implements EquipmentComponent    // LEAF
        wraps the existing Equipment entity

  class EquipmentZone implements EquipmentComponent      // COMPOSITE
        private final List<EquipmentComponent> children
        add(EquipmentComponent) / remove(...)
        getTotalUsageHours() -> children.stream()
                                 .mapToDouble(EquipmentComponent::getTotalUsageHours)
                                 .sum();

  Zones may nest (Main Floor > Cardio Zone > Treadmill Bank), which is what
  makes it a genuine Composite rather than a two-level list. Build at least
  one 3-level branch in the seed data so recursion is actually exercised.

  Payoff: calling getTotalUsageHours() on "Main Floor" recurses the whole
  tree with one line of client code. Zone-level utilisation feeds the
  Reports section of the Phase 8 sidebar.

  JUnit:
        - leaf usage hours == its own hours
        - zone total == sum of children (assert against a hand-computed value)
        - 3-level nesting aggregates correctly
        - empty zone returns 0, does not throw
        - adding a zone to itself -> rejected (cycle guard)


13.3 ATTENDANCE & CHECK-IN TRACKING
--------------------------------------------------
Closes a real hole: the system currently BOOKS sessions but never records
whether anyone attended - which means the existing "Total Hours Spent"
analytics figure is unsourced. This is a correctness fix disguised as a
feature, and it makes three already-built things honest.

  class Attendance implements Identifiable
        attendanceId, sessionId, memberId, enrollmentId
        LocalDateTime checkInTime, checkOutTime
        AttendanceStatus: BOOKED / CHECKED_IN / COMPLETED / NO_SHOW /
                          LATE_CANCELLED
        double hoursAttended   (derived from check-in/out)

  AttendanceService
        checkIn(memberId, sessionId)   validates:
              - booking exists            -> InvalidBookingException
              - session is today & within +/- 15 min of start
              - not already checked in    -> DuplicateDataException
        checkOut(...)  -> computes hoursAttended
        markNoShows()  -> batch job run on session end
        getAttendanceRate(memberId)  -> attended / booked

  THE CHAIN THIS COMPLETES (state this explicitly in the report - it is the
  best evidence that your features are designed, not bolted on):
        check-out -> hoursAttended
                  -> Equipment.cumulativeUsageHours (4.2)
                  -> threshold breach
                  -> auto MaintenanceLog created
                  -> Observer fires notification to Admin
                  -> Enrollment.sessionsCompleted increments (Phase 7)
                  -> member profile progress ring updates
  One check-out touches five subsystems. Demo it end-to-end in the video.

  Also: 3 consecutive NO_SHOWs on an enrolment -> notification to the
  member's instructor. Realistic, testable, and another Observer use.

  JUnit:
        - check-in outside the 15-min window -> InvalidBookingException
        - double check-in -> DuplicateDataException
        - check-out computes hours correctly (boundary: exactly 60 mins)
        - no-show marking flips only BOOKED rows, not CHECKED_IN
        - attendance rate maths with zero bookings -> no divide-by-zero
        - usage hours propagate to Equipment after check-out


13.4 WAITLIST WITH AUTO-PROMOTION  -> second Strategy use
--------------------------------------------------
Turns the existing capacity limit from a dead end into a workflow.

  class WaitlistEntry implements Identifiable
        entryId, sessionId, memberId, joinedAt, position
        WaitlistStatus: WAITING / PROMOTED / EXPIRED / DECLINED

  interface PromotionStrategy                    // STRATEGY #2
        WaitlistEntry selectNext(List<WaitlistEntry> queue);
        String getPolicyName();
  Implementations:
        FifoPromotionStrategy        - earliest joinedAt wins
        TierPriorityStrategy         - Premium tier first, then FIFO
        LoyaltyPromotionStrategy     - highest attendance rate wins
                                       (depends on 13.3 - build after it)

  WaitlistService
        join(sessionId, memberId)   -> only when session is at capacity
        onCancellation(sessionId)   -> strategy.selectNext() -> promote
                                    -> Observer notifies promoted member
                                    -> 2-hour window to confirm, else EXPIRED
                                       and the next member is promoted
        Admin can switch the active policy at runtime - SAME call site,
        different queue behaviour. That runtime swap is the polymorphism
        demo; do it live on camera.

  JUnit (rich test material - this is why it is worth building):
        - joining a non-full session -> rejected
        - FIFO ordering across 5 entries
        - tier priority overrides join order
        - cancellation promotes exactly one member
        - expired promotion cascades to the next in queue
        - promotion on a session that already started -> rejected
        - strategy swap changes outcome with identical input data
